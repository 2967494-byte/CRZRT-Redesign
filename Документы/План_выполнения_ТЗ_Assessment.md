## 0. Режим работ: локально → бой

### Принцип

| Поток | Кто | Что |
|-------|-----|-----|
| **A. Разработка** | Исполнитель | Полный функционал на локальном стенде (Docker / Linux VM) с PostgreSQL |
| **B. Инфраструктура** | Заказчик | `test.zakupki.tatar`, SSL, SMTP, DNS, доступы ЕСИА, реестры |

К моменту выдачи сервера цель — **выкатить уже работающий код** и только:
1. прописать `config` / `.env` (БД, SMTP, URL);
2. применить миграции + seed вопросов;
3. проверить HTTPS / почту / (позже) ЕСИА;
4. подключить модалку на основном портале.

**Не ждём** сервер, чтобы писать бизнес-логику.

### Локальный стенд (целевой)

```
Docker Compose (рекомендуется):

  ├── postgres     # PostgreSQL 16
  └── mailhog      # захват писем (пароль, Magic Link) без реального SMTP
```

Либо: PHP встроенный сервер / OpenServer + локальный PostgreSQL Windows/WSL.

**Базовый URL локально:** `http://localhost:8080` (или аналог)  
**Имитация домена:** в `config` — `APP_URL`, без жёсткой привязки к `test.zakupki.tatar`.

## 0.1. Решение по СУБД: PostgreSQL

**Принято:** для модуля Assessment на боевом сервере `test.zakupki.tatar` использовать **PostgreSQL** (Linux), а не MySQL/MariaDB основного портала.

### Почему это уместно

| Плюс | Пояснение |
|------|-----------|
| Изоляция от CMS | Основной портал остаётся на MySQL; Assessment не трогает его схему — как требует ТЗ §2.3 / §5.1.1 |
| Нагрузка | PostgreSQL удобнее для конкурентных сессий, индексов, JSONB (формулировки, порядок вопросов) |
| Типы данных | `timestamptz`, `inet` (IP), `jsonb`, `uuid` — под аналитику и аудит |
| Бэкапы | `pg_dump` / WAL — отдельный контур от `mysqldump` портала |

### Стек на бою (целевой)

| Компонент | Версия (мин.) |
|-----------|----------------|
| ОС | Linux (Ubuntu 22.04 / Debian 12 / аналог) |
| СУБД | **PostgreSQL 14+** (рекомендуется 15/16) |
| Кодировка | `UTF8`, locale `ru_RU.UTF-8` или `C.UTF-8` |
| PHP | 8.1+ (допустимо 7.4+) с расширением **`pdo_pgsql`** |
| Веб-сервер | Nginx + PHP-FPM (или Apache) |
| Пул | отдельная БД `asmt` / `assessment`, роль с минимальными правами |

### Отличие от формулировки в ТЗ Заказчика (§5.4.1)

В Приложении № 1 указаны MySQL/MariaDB. **Фактическая реализация — PostgreSQL** как более подходящая СУБД для изолированного high-load модуля. Это **не меняет** состав сущностей (`asmt_*`), только диалект SQL и драйвер.

**Действие:** зафиксировать в протоколе согласования / уточнении к ТЗ:  
> «Система управления базами данных модуля Assessment: PostgreSQL 14+ (Linux). Основной портал zakupki.tatar продолжает использовать MySQL.»

Префикс таблиц `asmt_` сохраняется (или схема PostgreSQL `asmt` + таблицы без префикса — на выбор; в коде единообразно).

### Технические следствия для разработки

1. PDO DSN: `pgsql:host=…;port=5432;dbname=…`  
2. Миграции: `SERIAL`/`GENERATED` / `BIGSERIAL`, `BOOLEAN`, `TIMESTAMPTZ`, `INET` для IP.  
3. Уникальность попытки: partial unique index `WHERE status = 'finished'`.  
4. JSON порядка вопросов / формулировок: тип **`JSONB`**.  
5. В поставке: `sql/schema.pgsql.sql` (+ опционально `pg_dump` seed).  
6. Бэкап (Заказчик): ежедневный `pg_dump -Fc` + хранение отдельно от бэкапов MySQL портала.  
7. Нагрузочный тюнинг этапа 4: `max_connections`, `shared_buffers`, `work_mem`, пул PgBouncer (при необходимости для 5000 сессий).

## 12. Порядок старта работ (первый спринт) — локально

**День 1 (kick-off, без ожидания сервера Заказчика):**
1. Поднять локальный Docker Compose: PHP + PostgreSQL + MailHog.  
2. Зафиксировать с Заказчиком: PostgreSQL, параллельные потоки A/B, ЕСИА «когда будут ключи».  
3. Запросить реестр организаций / дату поставки (не блокирует день 1–5).  
4. Создать каркас репозитория Assessment + `schema.pgsql.sql`.  

**День 1–2:**
5. Миграции, импорт 100 вопросов.  
6. `/register`, `/login`, каркас `/cabinet`.  

**К концу недели 1 (всё локально):**
7. Полный проход теста + Excel.  
8. Демо Заказчику (скринкаст / туннель ngrok при необходимости).  

**Когда Заказчик отдаст сервер:**
9. Выкат по `DEPLOY.md` (ожидаемо 0.5–1 день) + SMTP + DNS.  
10. Модалка на основном портале.  
11. ЕСИА и нагрузочный прогон — по готовности инфраструктуры.
